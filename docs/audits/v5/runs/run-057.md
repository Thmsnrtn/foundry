## Preconditions

Casey is evaluating Foundry for team adoption. Has added 5 test companies on Investor-Ready trial. Overnight, agents produced signals and decisions. Casey wants to measure: How long does morning triage take for 5 companies? Is it worth the $399/month?

## Transcript

### Step 1: Login and land on dashboard

Casey logs in. The dashboard loads for the currently selected company (via cookie).

**Codebase finding:** `src/routes/dashboard/index.ts` renders the signal dashboard. The layout context (`_shared.ts` line 48-174) loads in parallel: products, lifecycle state, DNA, next action, notifications, milestones, tour state. For the active product only -- not fleet-wide.

**Friction:** No fleet-level landing page. Casey lands on a single company's signal dashboard. To triage 5 companies, Casey must switch between them one by one. There is no "fleet summary" showing all companies' health at a glance.

**Result:** FRICTION (CRITICAL) -- No fleet-level triage dashboard. Morning triage requires O(n) navigation for n companies.

### Step 2: Check decision queue

Casey navigates to Decisions page to see pending items.

**Codebase finding:** `src/routes/dashboard/decisions.ts` renders the decision queue. Decisions are scoped by `productId`. There is no cross-company decision queue.

**Friction:** The decision queue shows only the current company's decisions. Casey must switch products 5 times to see all pending decisions. This violates J04 success criterion: "Decision queue is sorted by urgency, not chronology" -- there is no unified queue to sort.

**Result:** FRICTION (CRITICAL) -- Decision queue is per-company, not fleet-wide. Cannot triage across companies from a single view.

### Step 3: Check briefings

Casey navigates to the latest briefing for the current company.

**Codebase finding:** The sidebar shows "Briefing" link (`/agents/briefings/latest`) with a "NEW" dot badge. `src/routes/dashboard/agents-briefings.ts` renders the latest briefing. Briefings are per-product.

**Result:** PASS -- Briefing loads for current company.

### Step 4: Manual fleet triage cycle

Casey switches between all 5 companies using the product switcher, checking decisions and briefings for each.

**Codebase finding:** Product switcher is a `<select>` dropdown (layout.ts line 182) that POSTs to `/switch-product`. At 5 items, the dropdown is manageable. Each switch reloads the page (full page reload, not HTMX partial).

**Friction:** Each company switch requires: (1) click dropdown, (2) select company, (3) page reloads, (4) navigate to decisions, (5) review, (6) navigate to briefing, (7) review, (8) go back to switch again. For 5 companies, that's ~40 page loads. At NET-FAST this is ~30-60 seconds per company = 2.5-5 minutes total, which is within the 15-minute target. But the UX is purely repetitive click-work.

**Measurement:** Estimated triage time for 5 companies: 5-8 minutes (acceptable). But at 15 companies, this would be 15-24 minutes and violate the sub-linear scaling requirement.

**Result:** FRICTION (HIGH) -- Fleet triage is O(n) with no fleet-level aggregation. Acceptable at F5, fails at F15.

### Step 5: Evaluate for team adoption

Casey assesses: Can I present this to my CTO?

**Key observations for Casey's evaluation:**
1. No multi-seat support with per-company permissions -- blocker for team adoption (per Casey's abandonment trigger #1).
2. No admin console or usage analytics -- Casey cannot show "what the team is getting per dollar per company."
3. Product add/remove flow lacks fleet management ergonomics.

**Result:** FRICTION (HIGH) -- Three of Casey's abandonment triggers are hit: no multi-seat, no admin console, no usage analytics.

### Step 6: Cross-company boundary check

During product switching, Casey verifies each company shows its own data.

**Cross-company awareness check:** PASS. Cookie-based switching correctly isolates data. No residual data from previously viewed company appears after switching.

**Result:** PASS -- Boundaries maintained during rapid switching.
