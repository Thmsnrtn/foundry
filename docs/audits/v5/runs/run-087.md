# Run 087 — Casey (P08) x Company Retirement (J07)

**Persona:** Casey — VP Engineering evaluating for startup studio, Solo trial
**Journey:** Company retirement / archival
**Severity Baseline:** Casey's studio spins up and kills products quarterly. Retirement friction = adoption blocker.

---

## Simulation Transcript

### Step 1: Casey's core concern

Casey's voice: "We spin up and kill products quarterly. If retiring a company from Foundry is painful, we'll never adopt." This makes Journey 07 the make-or-break evaluation criterion for Casey.

### Step 2: Casey searches for retirement documentation

No documentation exists within the product about company retirement. The settings page has no "Retire" option. The privacy page has "Delete My Data" but not "Archive and Stop Monitoring."

### Step 3: Casey evaluates the product lifecycle model

From Casey's evaluation perspective:
- **Adding a product:** `/onboarding` flow — works but is per-product manual setup
- **Active monitoring:** SCP agents run automatically — works
- **Pausing:** No UI for pause. Schema supports `status='paused'` but no route exposes it.
- **Retiring/archiving:** No UI. Only hard deletion via privacy page.
- **Reactivating:** Impossible if deleted. No reactivation from archived state.

**Casey's evaluation report:** "The product lifecycle is binary: active or deleted. No intermediate states accessible from the UI. For a studio that routinely pauses, pivots, and re-evaluates products, this is a critical gap."

### Step 4: Casey considers the billing impact

If the studio has 10 active products and retires 3, the bill does not change (flat per-tier pricing). Casey notes: "We pay the same whether we have 3 active products or 10. The pricing model does not penalize product churn, but it also does not reward portfolio optimization."

### Step 5: Casey evaluates data preservation for retired products

The studio may want to reference historical data from retired products (post-mortems, pattern extraction for future products). Currently:
- Archived products return 404 (tenant middleware blocks access)
- Deleted products lose all data after 30 days
- No read-only archive view

**Casey's deal-breaker:** "If we retire a product and lose access to its agent recommendations and performance data, we cannot learn from it. Post-mortem analysis requires historical data access."

---

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | CRITICAL | **No retirement/archival flow.** Casey's primary adoption criterion is not met. The studio lifecycle (spin up, monitor, pause, retire, post-mortem) is not supported. |
| 2 | CRITICAL | **No historical data access for retired products.** Post-mortem analysis — critical for studio operations — is impossible once a product is archived or deleted. |
| 3 | HIGH | **No pause capability.** The studio cannot temporarily pause monitoring for a product under pivot without archiving or deleting it. |
| 4 | HIGH | **No bulk lifecycle management.** For 10+ products, each lifecycle transition must be done individually. No "retire these 3 products" bulk action. |
| 5 | MEDIUM | **Flat pricing does not reward portfolio optimization.** Retiring products does not reduce cost, removing a financial incentive for good portfolio hygiene. |

## Cross-Company Awareness Check

Casey's studio scenario is the strongest test of cross-company boundaries. With 8-12 products, some sharing codebases or customers, the retirement of one product should not affect others. Current implementation passes this check: products are fully isolated (each has its own SCP, data, and lifecycle). However, the `decision_patterns` table (global, no access controls) means patterns from a retired product could still influence active products.

## Verdict: JOURNEY FAILED — Retirement does not exist. Studio adoption blocked.
