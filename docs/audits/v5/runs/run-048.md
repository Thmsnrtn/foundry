## Step-by-Step Transcript

1. Morgan logs in. Navigates to Settings to evaluate the billing experience.
2. Settings loads. "Current Plan: Solo." "You have access to 5 features."
3. Morgan wants to evaluate the upgrade path. Sees only "Upgrade to Investor Ready" button. **No Growth tier option.**
4. Morgan clicks "Upgrade to Investor Ready." This POSTs to `/checkout` with `tier=investor_ready`.
5. **ERR-API injected**: Stripe returns 500. `createCheckoutSession` throws. The catch block in the checkout route:
   ```
   console.error('[CHECKOUT] Stripe session creation failed:', err);
   return c.redirect('/pricing?error=checkout_failed');
   ```
6. Morgan is redirected to `/pricing?error=checkout_failed`. **The pricing page is a public page (unauthenticated).** Morgan is now on a public page, logged in but viewing the public pricing grid.
7. **FRICTION**: The error is passed as a query parameter `error=checkout_failed` but the pricing page does not display error messages. Morgan sees the pricing grid with no indication of what went wrong.
8. Morgan tries again. Navigates back to Settings. Clicks "Upgrade to Investor Ready" again. Same Stripe 500. Same redirect to pricing page with no error displayed.
9. **FRICTION**: No error handling visible to the user. Morgan checks the browser console — no client-side error. The error is only logged server-side with `console.error` (not structured logging).
10. Morgan tries "Manage Subscription" instead. This POSTs to `/settings/manage-subscription`.
11. The handler creates a Stripe billing portal session. With ERR-API, `stripe.billingPortal.sessions.create` throws.
12. The catch block: `console.error('[BILLING] Portal session failed:', err); return c.redirect('/settings?error=billing_error');`
13. Morgan is redirected to `/settings?error=billing_error`. **Settings page does not display error messages from query params.** Morgan sees the same Settings page with no indication of failure.
14. **FRICTION**: Two separate billing operations fail silently. The `?error=` query parameters are set but never read or displayed by the Settings or pricing page templates.
15. Morgan inspects the network requests. Sees the 302 redirects with error params. Understands the failure but notes: "A non-technical user would have no idea why nothing happened."
16. Morgan checks: is there retry logic? **No.** Per the orientation doc, zero external calls have retry logic. The `withRetry` wrapper exists in the Stripe service but the checkout route in `settings.ts` does not use it.
17. Morgan examines the Settings route code (via behavior analysis): the `POST /checkout` handler imports `createCheckoutSession` but the catch block does not use `withRetry`. The Stripe service function `createCheckoutSession` does use `withRetry` internally, but the `POST /settings/manage-subscription` handler does NOT use a retry-wrapped function.

## Verdict

**FAILED**

Under Stripe API degradation, the entire billing flow fails silently. Users are redirected to pages that do not display error messages. Morgan identifies this as a fundamental reliability failure: no retry, no error display, no fallback. Even without the API error, the missing Growth tier upgrade path is a blocking issue.

## Recommendation

1. Consume `?error=` query params in Settings and pricing templates. Display a clear error banner: "Billing is temporarily unavailable. Please try again in a few minutes."
2. Add retry with exponential backoff on all Stripe portal and checkout operations.
3. Show all available tier upgrades (Solo -> Growth AND Solo -> Investor-Ready).
4. Replace `console.error` with structured logger in billing routes.
5. Add a fallback: if Stripe is unreachable, show current subscription details from the local database.
