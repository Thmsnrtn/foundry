## Preconditions

Taylor is signing up fresh (despite being persona 07, a returning user -- the condition matrix specifies ACCT-NEW and F0, so this is a new-account scenario). Taylor has a SaaS product with a GitHub repo and wants to get started.

## Transcript

### Step 1: Land on public marketing page

Taylor visits the Foundry landing page.

**Codebase finding:** `src/routes/public/landing.ts` renders the public landing page via `publicLayout()`. The page uses `layout()` with `showNav: false`, which means no sidebar, just header with "Log in" and "Get Started" buttons (layout.ts line 90-91).

**Result:** PASS -- Landing page renders with clear CTA buttons.

### Step 2: Click "Get Started" and sign up

Taylor clicks "Get Started" which links to `/auth/signup`.

**Codebase finding:** `src/routes/auth/clerk.ts` handles the auth flow using Clerk. The signup flow redirects to Clerk's hosted UI for email/password or OAuth (Google/GitHub).

**Result:** PASS -- Signup flow initiates via Clerk.

### Step 3: Post-auth redirect to onboarding

After Clerk signup, Taylor is redirected to the onboarding wizard.

**Codebase finding:** `src/routes/dashboard/onboarding.ts` handles the onboarding flow. The Clerk webhook (`src/routes/auth/clerk.ts`) provisions the founder record. Per orientation Problem #10, there is a race condition between the redirect and the webhook -- the onboarding page may load before the founder record exists. The auth middleware handles auto-provisioning if the webhook hasn't fired yet (orientation line 111).

**Friction:** If the webhook races with the redirect, Taylor may briefly see an error or empty state before the founder record is provisioned. The auto-provisioning fallback mitigates this, but there may be a flash of incorrect state.

**Result:** FRICTION (LOW) -- Potential race condition between Clerk webhook and redirect, mitigated by auto-provisioning.

### Step 4: Create first company

Taylor enters company name, GitHub repo URL, and description in the onboarding wizard.

**Result:** PASS -- Company creation form works.

### Step 5: GitHub OAuth and repo access

Taylor connects GitHub via OAuth to grant repository access.

**Codebase finding:** GitHub OAuth is part of the onboarding flow. The access token is stored in the `products` table as `github_access_token` (in plaintext per orientation Problem #3).

**Result:** PASS (with security concern) -- GitHub OAuth works but token is stored in plaintext.

### Step 6: Initial audit pipeline

The 8-step audit pipeline runs: stack detection, config, routes, billing, trust, errors, analytics, dependencies.

**Codebase finding:** `src/services/audit/` implements the pipeline. Each step calls GitHub API and potentially Anthropic Claude. No retry logic or timeout on these external calls (orientation Problem #1).

**Friction:** If any audit step fails (GitHub API rate limit, Anthropic timeout), the entire pipeline may hang or produce incomplete results. No user-facing progress indicator was identified in the route handlers. Taylor sees either a loading state or a redirect to the dashboard.

**Result:** FRICTION (MEDIUM) -- Audit pipeline lacks progress indication and has no resilience to external API failures.

### Step 7: SCP provisioning and first briefing

12 SCP agents are provisioned. First agent cycle runs and produces a briefing.

**Codebase finding:** SCP provisioning failures are silently swallowed (orientation Problem #10). If provisioning fails, Taylor's dashboard may show no agent activity.

**Friction:** Success criterion requires "Time from signup click to first live briefing is under 5 minutes." The audit pipeline, SCP provisioning, and first agent cycle are sequential. Each involves external API calls (GitHub, Anthropic). At NET-FAST with no errors, the total time may exceed 5 minutes depending on API response times.

**Result:** FRICTION (MEDIUM) -- Time-to-first-briefing may exceed 5-minute target due to sequential external API calls.

### Step 8: Dashboard with live SCP data

Taylor lands on the dashboard and sees the first briefing data.

**Codebase finding:** The dashboard (`src/routes/dashboard/index.ts`) loads layout context with risk state, next action, notifications, and milestones. For a brand-new company, most of this data will be default/empty until the first agent cycle completes.

**Result:** PASS (conditional) -- Dashboard loads, but initial data may be sparse until first agent cycle completes.
