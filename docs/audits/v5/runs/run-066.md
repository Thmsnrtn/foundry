## Preconditions

## Transcript

### Step 1: Assess layout on tablet (1024x768)

Sam loads the dashboard on a 1024px-wide tablet.

**Codebase finding:** layout.ts renders a sidebar + main content layout. The body class is `has-sidebar` when `showNav` is true. The sidebar is a `<nav class="sidebar">` with fixed positioning controlled by CSS. On 1024px, the sidebar and main content must share the screen. Without inspecting `styles.css`, the sidebar is likely 200-250px wide, leaving ~770-824px for the main content.

**Friction:** The mobile bottom nav (`mobilBottomNav`) is rendered when `productId` exists (layout.ts line 108). It appears to be designed for mobile viewports, but may also render on tablet. If both sidebar and mobile bottom nav render on tablet, there is UI duplication.

**Result:** FRICTION (LOW) -- Tablet layout is likely functional but may have sidebar compression or dual-nav rendering.

### Step 2: Product switcher at 6 companies on tablet

Sam uses the product switcher to navigate between companies.

**Codebase finding:** The product switcher `<select>` at 6 items is a native HTML select. On a tablet, native selects typically open a wheel picker (iOS) or dropdown (Android). At 6 items, this is manageable.

**Result:** PASS -- Product switcher functional on tablet at 6 companies.

### Step 3: Add company #7

Sam attempts to add a 7th company.

**Codebase finding:** Same pattern as other add-company findings. The add-company entry point is not in the sidebar or dashboard. Sam must navigate to product management or settings.

**Result:** FRICTION (MEDIUM) -- Add-company path not discoverable (duplicate of F-053-A).

### Step 4: Dashboard performance at 6 companies

Sam navigates between companies, measuring perceived load time.

**Codebase finding:** `_shared.ts` makes 7+ parallel DB queries on each page load. At NET-AVG (80ms latency), each query round trip is ~160ms. With 7 parallel queries, the total is ~160ms (parallel execution) + server processing + network transfer. On a 10 Mbps connection, a typical dashboard page (estimated 50-100KB HTML) transfers in ~40-80ms. Total estimated load time: ~300-500ms.

**Result:** PASS -- Performance is acceptable on NET-AVG at F5. SSR architecture keeps payload sizes manageable.

### Step 5: Fleet-level sorting and filtering

J03 requires: "Companies can be sorted by health, MRR, risk state, last-updated."

**Codebase finding:** There is no fleet view with sortable company list. The product switcher is a simple `<select>` dropdown with no sorting. The dashboard shows one company at a time.

**Result:** FRICTION (CRITICAL) -- No fleet view with sorting/filtering capabilities. J03 success criteria unmet.

### Step 6: Batch operations

J03 requires: "Batch actions available: approve all low-risk remediations, dismiss info signals."

**Codebase finding:** No batch operations exist across companies. Each remediation and signal is handled per-company. There is no cross-company batch UI.

**Result:** FRICTION (CRITICAL) -- No batch operations across companies.

### Step 7: Cross-company boundary check

**Cross-company awareness check:** PASS. Product switching on tablet uses the same cookie-based mechanism. No boundary issues.

**Result:** PASS -- Boundary maintained.
