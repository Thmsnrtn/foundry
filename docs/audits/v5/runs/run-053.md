## Preconditions

Alex has one active company with 2+ weeks of SCP data on Growth tier. Wants to add a second SaaS product. Growth tier permits multi-company.

## Transcript

### Step 1: Find "Add Company" action

Alex is on the dashboard for Company A. Looks for a way to add a second company.

**Codebase finding:** The product switcher in layout.ts line 178-188 renders a `<select>` dropdown only when `allProducts.length > 1`. Since Alex has only 1 product, the switcher does not appear -- just a static breadcrumb with the company name. There is no visible "Add Company" button in the header or sidebar. Alex must navigate to Settings or Products to find the add-company flow.

`src/routes/dashboard/products.ts` likely contains the product management page. The command palette (layout.ts line 124-152) does not include an "Add Company" or "New Product" entry.

**Friction:** The "add company" action is not discoverable from the main dashboard when the user has only 1 company. The product switcher is hidden (it only appears at 2+ products). No "+ Add" button in the sidebar or header.

**Result:** FRICTION (HIGH) -- The 1-to-2 company transition has no discoverable entry point from the main dashboard.

### Step 2: Navigate to Products page

Alex clicks Settings in the sidebar footer, then looks for a products or companies section.

**Codebase finding:** The sidebar has Settings at the bottom (layout.ts line 320). The settings page presumably links to product management. The sidebar also has no explicit "Companies" or "Products" nav item in the standard sections.

**Result:** PASS (with friction) -- Alex eventually finds the products management, but the path is indirect.

### Step 3: Add second company

Alex finds the "Add Product" form and enters: name, GitHub repo URL, description.

**Codebase finding:** The product creation flow requires GitHub repo URL. `src/routes/dashboard/products.ts` handles product creation. GitHub OAuth is needed to grant repo access.

**Result:** PASS -- Company creation form works. GitHub OAuth flow initiates.

### Step 4: Second company audit and SCP provisioning

After GitHub connection, the audit pipeline runs for the second company. SCP provisions 12 agents.

**Codebase finding:** SCP provisioning is handled by `src/services/scp/provisioner.ts`. The 8-step audit pipeline runs via `src/services/audit/`. Provisioning failures are silently swallowed per orientation doc (Problem #10).

**Friction:** If SCP provisioning fails silently, Alex would see a company added but no agent activity. There is no explicit progress indicator or success confirmation visible in the codebase's route handlers.

**Result:** FRICTION (MEDIUM) -- Silent SCP provisioning failures could leave the second company without agents, with no user-facing error.

### Step 5: Fleet view with two companies

After adding the second company, Alex should see both companies in a fleet view.

**Codebase finding:** With 2 products, `allProducts.length > 1` becomes true, so the product switcher `<select>` now appears in the header (layout.ts line 181-182). However, there is no dedicated fleet-view page showing both companies side-by-side. The dashboard shows one company at a time, with switching via the dropdown.

**Friction:** No fleet overview at the 2-company level. The experience is "single company + a dropdown to switch" rather than "fleet view with both companies visible." The value proposition of multi-company is not immediately visible.

**Result:** FRICTION (HIGH) -- No fleet view at the critical 1-to-2 transition. Both companies are only accessible one-at-a-time via dropdown.

### Step 6: Cross-company boundary check

Alex switches to Company B and verifies dashboard data.

**Cross-company awareness check:** PASS. Switching via the product `<select>` POSTs to `/switch-product`, updates the cookie, and all subsequent queries scope to the new product ID.

**Result:** PASS -- Boundary correctly maintained.
