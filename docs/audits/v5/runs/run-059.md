## Preconditions

Devon uses VoiceOver on Mac. Has 2 companies on Growth tier. Wants to navigate Settings, review billing, and switch between companies -- all via keyboard and screen reader.

## Transcript

### Step 1: Page load and skip link

Devon loads the dashboard. VoiceOver announces the page title.

**Codebase finding (actual ARIA in layout.ts):**
- Line 74: `<a href="#main-content" class="skip-link">Skip to main content</a>` -- skip link is present.
- Line 63: `<html lang="en">` -- language attribute is set.
- Line 99: `<main id="main-content">` -- main landmark is present.
- Line 293: `<nav class="sidebar">` -- sidebar is a `<nav>` element but lacks `aria-label`. VoiceOver will announce "navigation" but not "sidebar navigation" vs "main navigation."

**Friction:** Sidebar `<nav>` has no `aria-label` to distinguish it from mobile bottom nav (which does have `aria-label="Main navigation"` at line 342). VoiceOver users cannot distinguish between the two navigation landmarks.

**Result:** FRICTION (HIGH) -- Sidebar nav lacks `aria-label`. Screen reader users cannot distinguish between navigation regions.

### Step 2: Navigate sidebar via keyboard

Devon tabs through the sidebar to find Settings.

**Codebase finding (actual ARIA in layout.ts):**
- Sidebar items are rendered as `<ul class="sidebar-nav">` with `<li><a href="...">` links (layout.ts line 356-369). Standard anchor elements are keyboard-focusable.
- The command palette button (line 294) is a `<button>` -- keyboard accessible.
- Section headers use `<details>/<summary>` for collapsible sections (line 301). The AGENTS section has `<details open>`, but FORWARD/SIGNALS/AUTONOMY/SYSTEM use `sectionHeader()` which returns a `<div>` -- these are not collapsible and not interactive.

**Friction:** Navigation structure is inconsistent. AGENTS section is in a `<details>` element (keyboard-accessible, collapsible). Other sections (FORWARD, SIGNALS, AUTONOMY, SYSTEM) are plain `<div>` headers. The inconsistency means VoiceOver announces the AGENTS group differently from others.

**Result:** FRICTION (MEDIUM) -- Inconsistent sidebar section structure between collapsible (details/summary) and static (div) groups.

### Step 3: Product switcher with screen reader

Devon needs to switch between the 2 companies using the product switcher.

**Codebase finding (actual ARIA in layout.ts):**
- Product switcher at line 178-188 uses a `<select>` inside a `<form>` with `onchange="this.form.submit()"`. The `<select>` has `name="product_id"` but NO `<label>` element and NO `aria-label`. VoiceOver will announce "popup button" with no context about what it does.
- The breadcrumb span wrapping it has "/" as text content, which VoiceOver will read as "slash."

**Result:** FRICTION (CRITICAL) -- Product switcher `<select>` has no accessible label. Screen reader announces "popup button" with no context. This is Devon's abandonment trigger #1: "If I can't tab to it and hear what it does, it doesn't exist to me."

### Step 4: Notification bell accessibility

Devon tabs to the notification bell in the header.

**Codebase finding (actual ARIA in layout.ts):**
- Notification bell at line 192-215 uses `<details class="notif-bell">` with `<summary>` containing only the emoji `bell`. No `aria-label` on the `<summary>`. VoiceOver will announce "disclosure triangle" or read the emoji as "bell" (depending on emoji support), but there is no semantic meaning.
- The notification count `<span class="notif-count">` has no `aria-label`. VoiceOver may or may not read the number.

**Result:** FRICTION (CRITICAL) -- Notification bell has no `aria-label`. Screen reader cannot determine the purpose or count. Icon-only interactive element without accessible name violates WCAG 4.1.2.

### Step 5: Settings page form controls

Devon navigates the Settings page.

**Codebase finding:** Settings page form controls were not fully inspected, but based on the privacy.ts pattern, form inputs do have `<label>` elements with `for` attributes (privacy.ts lines 217, 228-229, 238-239). This is a positive pattern.

**Result:** PASS -- Form controls in Privacy settings have associated labels.

### Step 6: Delete confirmation modal accessibility

Devon explores the delete data flow in Privacy.

**Codebase finding (actual code in privacy.ts line 291-310):**
- Delete modal: `<div id="delete-modal" style="display:none;...">`. No `role="dialog"`, no `aria-modal="true"`, no `aria-label`. Opening the modal uses `onclick="document.getElementById('delete-modal').style.display='flex'"` -- no focus management. Closing uses `onclick="...style.display='none'"` -- no focus return.
- Compare with command palette (layout.ts line 112): `role="dialog" aria-label="Command palette" aria-modal="true"` -- correctly implemented.

**Result:** FRICTION (CRITICAL) -- Delete confirmation modal lacks `role="dialog"`, `aria-modal`, `aria-label`, focus trap, and focus return. Screen reader users may not perceive the modal at all. Focus is not moved into the modal when opened.

### Step 7: Cross-company boundary check

Devon switches between companies using the inaccessible product switcher.

**Cross-company awareness check:** Boundary isolation is maintained technically, but the switching mechanism is inaccessible. Devon may not be able to reliably switch companies via screen reader due to the unlabeled `<select>`.

**Result:** PASS (technical boundary) / FAIL (accessible boundary) -- Data isolation works but the switching mechanism is inaccessible.
