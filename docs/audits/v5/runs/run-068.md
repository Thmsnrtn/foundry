## Preconditions

Taylor has been away for 6 weeks. Returns to find 2 companies. One product was shut down during the absence. Taylor wants to retire the dead company from Foundry so the fleet view shows only the live product.

## Transcript

### Step 1: Return after absence -- catch-up state

Taylor logs back in after 42 days. The dashboard loads for the default product (first in cookie or list).

**Codebase finding:** `_shared.ts` resolves the active product from cookie priority. If the cookie still references the dead product, Taylor lands on the dead product's dashboard. There is no "welcome back" or "catch-up" summary.

**Friction:** Taylor's core need is a catch-up briefing covering the 42-day absence. This is Taylor's persona scenario. The signal timeline has accumulated 6 weeks of data. Decisions have queued up. But the dashboard shows current state, not a retrospective summary.

**Result:** FRICTION (HIGH) -- No catch-up or absence summary for returning users. Taylor must manually reconstruct 6 weeks of activity.

### Step 2: Assess which company to retire

Taylor switches between the 2 companies to see which one is the dead product.

**Codebase finding:** Product switcher shows both companies by name. The dashboard for the dead product presumably shows stale data -- last agent cycle was whenever the product was still active. Risk state may have shifted to yellow or red due to inactivity.

**Result:** PASS -- Taylor can identify the dead product by examining each company's dashboard.

### Step 3: Find company retirement flow

Taylor looks for a way to remove the dead company.

**Codebase finding:** Same as F-061-A. The retirement flow is in Privacy & Data settings, labeled as "Delete My Data." No "Archive Company" or "Retire Company" option exists in Settings or the product management page.

**Friction:** Taylor specifically wants to "retire" the company (keep it in history but stop agents), not "delete" it. The only option is permanent deletion. There is no archive/pause state for companies.

**Result:** FRICTION (CRITICAL) -- No company archive/pause option. Only permanent deletion exists. Taylor cannot retire a company while preserving its historical data.

### Step 4: Attempt to stop agents without deleting

Taylor looks for a way to pause or stop the SCP agents for the dead company without deleting all data.

**Codebase finding:** The orientation doc mentions company lifecycle: "SCP instance lifecycle (provision/pause/retire/migrate): Basic provision only (Current) | Full lifecycle (Target)." There is no pause or retire mechanism for SCP agents. Agents continue running on hourly cron regardless of product state.

**Friction:** SCP agents are burning AI credits (Anthropic API calls) for a dead product. Taylor cannot stop this without deleting the company entirely. This wastes money and pollutes the decision queue with recommendations for a defunct product.

**Result:** FRICTION (CRITICAL) -- No SCP pause/retire. Agents continue running (and consuming API credits) for dead products.

### Step 5: Decide whether to delete

Taylor weighs options: delete and lose all historical data, or leave the dead company running and pay for useless agent cycles.

**Result:** FRICTION (HIGH) -- Binary choice between permanent deletion and continued wasteful operation. No middle ground.

### Step 6: Cross-company boundary check

Taylor switches between the live and dead company. Data is correctly scoped.

**Cross-company awareness check:** PASS. The dead company's stale data does not contaminate the live company's dashboard.

**Result:** PASS -- Boundary maintained.
