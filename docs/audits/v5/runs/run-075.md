## Preconditions

Jamie has 3 companies on Growth tier. One product has been shut down. Jamie wants to retire it from Foundry. Using a tablet on a slow network.

## Transcript

### Step 1: Page load on slow network + tablet

Jamie loads the Foundry dashboard on a tablet at 2 Mbps with 300ms latency.

**Codebase finding:** The page requires `styles.css` and `htmx.min.js`. At 2 Mbps, a 100KB CSS file takes ~400ms to download, plus 300ms latency = ~700ms per resource. Total blocking CSS + JS load time: ~1.5-2 seconds. The HTML itself is server-rendered, so content is partially visible before resources load. HTMX is deferred (layout.ts line 71), so HTMX-driven interactions won't work until it loads.

**Friction:** On NET-SLOW, the initial page load is 2-3 seconds (acceptable). However, every subsequent navigation (each page is a full page reload, not SPA-style) also takes 2-3 seconds. If cached resources are available, subsequent loads are faster.

**Result:** FRICTION (LOW) -- 2-3 second initial load on NET-SLOW. Acceptable due to SSR architecture. Subsequent navigations benefit from caching.

### Step 2: Navigate to Privacy & Data on tablet

Jamie navigates through the sidebar to Privacy & Data.

**Codebase finding:** On a 1024px tablet, the sidebar may be compressed or hidden behind a hamburger menu (depends on CSS). The mobile bottom nav (layout.ts line 108) renders when `productId` exists, but it only has Signal, Decisions, Agents, Plan, and More tabs -- Privacy is not in the mobile nav. Jamie must use the sidebar to reach Privacy.

**Friction:** If the sidebar is hidden on tablet (1024px is borderline between desktop and tablet breakpoints), Jamie may need to toggle it open. Privacy is accessible only through the sidebar, not the mobile bottom nav.

**Result:** FRICTION (MEDIUM) -- Privacy not accessible via mobile bottom nav. Sidebar behavior on 1024px tablet is CSS-dependent and may be hidden.

### Step 3: Initiate company retirement

Jamie clicks "Delete My Data" for the dead product.

**Codebase finding:** Same deletion flow as previous runs. Modal opens with confirmation dialog.

**Friction on tablet:** The delete modal (privacy.ts line 291) uses `position:fixed;inset:0` for the overlay and `max-width:440px` for the dialog. On a 1024x768 tablet, the modal should render properly. The dialog padding and button layout should fit.

**Result:** PASS -- Delete modal renders acceptably on 1024px tablet.

### Step 4: Confirm deletion on slow network

Jamie confirms deletion. POST `/privacy/delete` is submitted.

**Codebase finding:** The POST request to `/privacy/delete` calls `scheduleDataDeletion` and redirects to `/privacy?success=deletion_scheduled`. On NET-SLOW, the POST round trip takes ~600-1000ms (300ms up + processing + 300ms redirect response + 300ms reload).

**Friction:** The form submission on slow network has no loading indicator. The button click may appear to do nothing for ~1 second before the redirect. Users may double-click, potentially submitting twice (though the `scheduleDataDeletion` function should be idempotent).

**Result:** FRICTION (LOW) -- No form submission loading indicator on slow network. Potential double-click issue.

### Step 5: Verify remaining companies

After deletion, Jamie switches to the remaining 2 companies to verify they are unaffected.

**Cross-company awareness check:** PASS. The product switcher still shows 3 companies (including the zombie). Switching to the live companies shows their correct data.

**Result:** PASS -- Boundary maintained.

### Step 6: Attempt to find the retired product's history

Jamie wants to see historical data from the retired product (past decisions, briefings) for reference on other projects.

**Codebase finding:** Once the product is deleted (after 30-day delay), all data is gone. During the 30-day window, the product is still accessible (zombie state) with full data. But there is no "export before deletion" prompt or automatic pre-deletion export.

**Friction:** Jamie may lose valuable historical data. The deletion flow does not remind users to export before confirming. The modal text mentions "We recommend exporting your data before proceeding" with a link (privacy.ts line 299), but this is in the modal body, which users scanning for the confirm button may miss.

**Result:** FRICTION (MEDIUM) -- Export recommendation in deletion modal may be overlooked. No automatic pre-deletion export.
