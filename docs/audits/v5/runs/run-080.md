# Run 080 — Jordan (P06) x Full Org Deletion (J10)

**Persona:** Jordan — compliance-minded fintech founder, Growth tier, 1 company
**Journey:** Full organization deletion (churn path)
**Severity Baseline:** Jordan needs clean, documented deletion with proof for regulatory files.

---

## Simulation Transcript

### Step 1: Jordan navigates to deletion flow

Jordan goes to `/privacy`. The "Request Account Deletion" section is at the bottom of the page. It says: "Permanently delete your product and all associated data. This action cannot be undone. Please export your data first."

Good: the option is visible and self-service. Jordan does not need to email support.

### Step 2: Jordan clicks "Delete My Data"

A modal appears with:
- Title: "Confirm Data Deletion"
- Warning: "This will permanently schedule deletion of all your product data including metrics, briefings, decisions, and agent logs. This cannot be undone."
- Export reminder: "We recommend exporting your data before proceeding."
- "Cancel" and "Yes, Delete Everything" buttons

**Problem 1:** The modal says "all your product data" — but this is per-product deletion, not organization deletion. The `scheduleDataDeletion` function takes a single `productId`. Jordan has 1 product, so it works, but a multi-product founder would need to delete each product individually. There is no "delete everything for all my products" option.

**Problem 2:** The confirmation requires only a button click. No "type your organization name" challenge. No re-authentication. For a compliance-minded founder doing a permanent destructive action, this is surprisingly easy to accidentally trigger.

### Step 3: Jordan clicks "Yes, Delete Everything"

The handler calls `scheduleDataDeletion(productId, 30)`. This:
1. Inserts a `data_deletion_scheduled` event into `agent_audit_log`
2. Redirects to `/privacy?success=deletion_scheduled`

**CRITICAL: This does NOT:**
- Cancel the Stripe subscription
- Stop SCP agents
- Revoke GitHub tokens
- Create a `deletion_requests` table entry (the GDPR job looks at `deletion_requests`, not `agent_audit_log`)
- Send a confirmation email
- Show a grace period countdown
- Provide a receipt or timestamp

**Codebase evidence:** `src/services/privacy/consent.ts` lines 290-308 — `scheduleDataDeletion` only writes to `agent_audit_log`. It does not interact with Stripe, GitHub, or the `deletion_requests` table.

### Step 4: Jordan checks what happens after scheduling

The `processScheduledDeletions()` function (`src/services/privacy/consent.ts` lines 316-372) finds `data_deletion_scheduled` events that are past their threshold. It deletes product data from ~14 tables and sets `products.status='deleted'`.

**But:** It does NOT:
- Delete the `founders` row
- Cancel the Stripe subscription
- Revoke GitHub tokens
- Delete notifications, milestone events, or other founder-level data
- Send a deletion confirmation email

Meanwhile, the `processAccountDeletions()` function in `src/jobs/gdpr.ts` (lines 86-145) is a separate, more comprehensive deletion pipeline that:
- Processes `deletion_requests` with 30-day grace period
- Deletes product data + founder data + all associated records
- Does handle founder-level cleanup

**But the privacy page never creates a `deletion_requests` entry.** The two systems are completely disconnected.

### Step 5: Jordan checks for billing cancellation

After initiating deletion via the privacy page:
- Stripe subscription continues charging
- SCP agents continue running
- GitHub integration remains connected
- Jordan keeps getting charged for a product that is "scheduled for deletion"

The only way to stop billing is to separately go to Settings > Manage Subscription > Cancel via Stripe Portal. The deletion flow does not do this.

### Step 6: Jordan checks for grace period / recovery

The `processScheduledDeletions` function checks if enough time has passed since scheduling. But there is no UI to:
- See the deletion countdown
- Cancel the scheduled deletion
- Recover data during the grace period

Once scheduled, the product will be deleted when the cron job next runs after 30 days. There is no undo button.

### Step 7: Jordan checks for deletion receipt

No confirmation email is sent. No deletion receipt is generated. The only evidence is the `agent_audit_log` entry, which Jordan cannot access after the product is deleted (tenant middleware returns 404 for archived/deleted products).

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | CRITICAL | **Two disconnected deletion systems.** The privacy page uses `scheduleDataDeletion` (writes to `agent_audit_log`). The GDPR job uses `deletion_requests` table. They never intersect. The privacy page deletion is incomplete; the GDPR job deletion is unreachable from UI. |
| 2 | CRITICAL | **Billing does not stop on deletion.** `scheduleDataDeletion` does not cancel the Stripe subscription. Jordan keeps getting charged during the 30-day grace period and beyond if the cron job fails. |
| 3 | CRITICAL | **SCP agents continue running after deletion scheduled.** No `deprovisionSCP()` call. Agents keep running, accumulating data for a product that is marked for deletion. |
| 4 | CRITICAL | **GitHub tokens not revoked.** No GitHub token revocation on deletion. The token remains in the database (nulled only by `processScheduledDeletions` setting `github_access_token = NULL`), but it is not revoked via GitHub API. The token remains valid on GitHub's side. |
| 5 | HIGH | **No confirmation challenge.** Deletion requires only one button click. No "type your product name" or re-authentication. For Jordan's regulatory context, accidental deletion of compliance data is catastrophic. |
| 6 | HIGH | **No deletion receipt or confirmation email.** No email confirming what was deleted and when. No exportable proof of deletion. Jordan cannot show their auditor evidence that data was removed. |
| 7 | HIGH | **No recovery UI.** No way to cancel a scheduled deletion. No grace period dashboard. No "undo" within the 30-day window. |
| 8 | HIGH | **Per-product deletion, not org-wide.** The privacy page deletes the currently-selected product. For multi-product founders, each product must be deleted individually. There is no "delete my entire organization" flow. |
| 9 | MEDIUM | **Deletion proof becomes inaccessible.** The `agent_audit_log` entry proving deletion was scheduled is on the product that gets deleted. After deletion, the tenant middleware blocks access, so the proof is unreadable. |

## Cross-Company Awareness Check

**No boundary violation** because Jordan has 1 company. However, for a multi-product founder, the per-product deletion model means:
- Deleting Product A does not affect Product B (correct isolation)
- But there is no "delete all" that ensures nothing is left behind
- The `deletion_requests` system (GDPR job) operates at founder level, but the privacy page operates at product level — a fundamental architectural mismatch

## Verdict: JOURNEY FAILED — Deletion is cosmetic. Billing continues, agents run, tokens persist, no receipt issued.
