## Step-by-Step Transcript

1. Sam logs in. Has decided to leave Foundry. Wants to delete everything.
2. Portfolio view shows 5 companies. Sam navigates to Privacy (`/privacy`).
3. Sam reads the "Your Data" section. Sees "Delete My Data" button. Reads the description: "Permanently delete your product and all associated data."
4. **FRICTION**: Sam has 5 companies. "Delete My Data" acts on the currently selected product (Company A). Sam needs to delete all 5.
5. Sam clicks "Delete My Data." Modal says "all your product data." Sam reads carefully and realizes this might be per-product.
6. Sam clicks "Yes, Delete Everything." Company A deletion scheduled.
7. Sam navigates to portfolio. Company A still visible. Sam switches to Company B, navigates to Privacy, deletes. Repeats for C, D, E.
8. **5 separate deletion cycles.** Each requires: portfolio -> click product -> Privacy -> Delete -> Confirm -> back to portfolio. Total time: ~5 minutes.
9. **FRICTION**: No batch deletion. No "Delete All Companies" or "Close Account" option.
10. After all 5 deletions scheduled: Sam checks Settings. Products still listed. No "pending deletion" indicators.
11. **Sam now needs to cancel the Stripe subscription.** Navigates to Settings -> "Manage Subscription" -> Stripe portal.
12. In Stripe portal, Sam cancels the subscription. Returns to Foundry.
13. **FRICTION**: Had to separately cancel billing. The deletion flow should have offered this.
14. **ERR-API injected**: GitHub API returning 500. When `processScheduledDeletions` runs after 30 days, it sets `github_access_token = NULL` in the database but does NOT revoke the token at GitHub's API. Even without the error, the code never calls GitHub's token revocation endpoint.
15. **FRICTION**: Sam's 5 GitHub integration tokens are orphaned. They remain valid at GitHub even though Foundry nullified them locally. This is a security issue.
16. Sam checks: Is there a confirmation email? **No.** No email sent for any of the 5 deletions.
17. Sam has no proof of deletion request. No receipt, no confirmation, no audit trail visible to the user.
18. After 30 days (simulated): `processScheduledDeletions` runs for each product. Deletes data from 14 tables. Sets product status to `deleted`. Founder account and `founders` table entry persist. The `processAccountDeletions` function was never triggered because no `deletion_requests` record was created.
19. Sam's account still exists with 0 active products and a cancelled Stripe subscription.

## Cross-Company Awareness Check

- **Sequential deletion**: Sam correctly identified and deleted each product individually. Product names visible in the portfolio grid.
- **Cookie management**: Product switching via portfolio works correctly. Each deletion targeted the right product.
- **CRITICAL**: No account-level deletion. Even after deleting all 5 products, the founder account persists. Personal data (name, email, Stripe customer ID) remains in the `founders` table indefinitely.

## Verdict

**FAILED**

Full organization deletion requires 5 separate deletion cycles, a separate Stripe cancellation, and still leaves the founder account and PII in the database. GitHub tokens are not revoked at the API level. No confirmation, no receipt, no proof of deletion. Fails GDPR requirements.

## Recommendation

1. Build a "Close Account" endpoint that: cancels Stripe subscription, schedules ALL products for deletion, creates a `deletion_requests` record, revokes all GitHub tokens at the API level, sends confirmation email.
2. Add batch product deletion: "Delete all products and close account."
3. The `processScheduledDeletions` function should delete from ALL tables with product_id foreign keys, not a hardcoded list of 14.
4. Implement GitHub token revocation via the GitHub API (not just nullifying locally).
5. Send a deletion confirmation email with a timeline and reactivation instructions.
