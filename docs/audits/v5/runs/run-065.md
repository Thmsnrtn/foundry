## Preconditions

Sam is shutting down 6 companies and wants to fully delete all data and the account. Sam is technical and wants to verify that deletion is thorough -- database records, cached data, GitHub tokens, Stripe associations.

## Transcript

### Step 1: Pre-deletion data audit

Sam wants to verify exactly what will be deleted before initiating.

**Codebase finding:** The deletion modal (privacy.ts line 294) says: "permanently schedule deletion of all your product data including metrics, briefings, decisions, and agent logs." This is a subset -- it does not mention GitHub access tokens, Stripe billing data, or Clerk auth data.

**Friction:** Sam, being technical, wants an exhaustive list. The schema has 16 core tables plus ~40 from migrations. The deletion presumably targets product-scoped data but the modal does not enumerate what. For Sam's data-driven mindset, this is insufficient.

**Result:** FRICTION (HIGH) -- Deletion scope is vaguely described. Does not enumerate all data types being deleted or retained.

### Step 2: Verify GitHub token cleanup

Sam is concerned about the GitHub access token stored for each company.

**Codebase finding:** Per orientation doc Problem #3: "GitHub access tokens stored in plaintext (schema says 'Encrypted' but no encryption code)." The `products` table stores `github_access_token` in plaintext. When a product is deleted, this token must be revoked and the record deleted.

**Friction:** The deletion flow (via `scheduleDataDeletion`) presumably deletes the product record, which would remove the token from the database. But does the deletion also revoke the GitHub OAuth token? Without revocation, the token remains valid on GitHub's side even after Foundry deletes its copy.

**Result:** FRICTION (CRITICAL) -- GitHub access tokens may not be revoked during deletion. Plaintext storage (orientation Problem #3) means tokens persist in database backups even after deletion.

### Step 3: Execute serial deletion for 6 companies

Sam must delete each of the 6 companies individually.

**Result:** FRICTION (HIGH, duplicate of F-063-A) -- No fleet-level deletion. 6 individual deletion processes required.

### Step 4: Verify data is actually removed

Sam wants confirmation that data has been purged from the database, not just soft-deleted.

**Codebase finding:** `scheduleDataDeletion(ctx.productId, 30)` implies a 30-day delay. The actual deletion logic is in `src/services/privacy/consent.ts`. Without inspecting this service in detail, it is unclear whether the deletion is hard (DROP rows) or soft (mark as deleted). Sam wants a "receipt" -- a verifiable confirmation that deletion occurred.

**Friction:** Robin's voice applies here too: "I want a receipt that says 'all data deleted' with a timestamp." No such receipt or confirmation email is visible in the codebase.

**Result:** FRICTION (HIGH) -- No deletion receipt or confirmation. Cannot verify that data was actually removed vs. soft-deleted.

### Step 5: Account deletion vs. product deletion

After deleting all 6 products, Sam wants to delete the founder account itself.

**Codebase finding:** There is no account/founder deletion flow in the routes. The privacy page deletes product data but not the founder record or Clerk user. Sam's account persists even after all products are deleted.

**Result:** FRICTION (HIGH) -- No founder account deletion. Deleting all products leaves an orphaned founder account.

### Step 6: Cross-company boundary check

During serial deletion, Sam verifies each company's deletion is independent.

**Cross-company awareness check:** PASS. Deleting Company A does not trigger deletion of Company B's data. Each `scheduleDataDeletion` call is scoped to a specific `productId`.

**Result:** PASS -- Deletion is correctly scoped per product.
