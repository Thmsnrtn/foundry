# Run 090 — Casey (P08) x Full Org Deletion (J10)

**Persona:** Casey — VP Engineering evaluating for startup studio, Solo trial
**Journey:** Full organization deletion (churn path)
**Severity Baseline:** Casey needs to confirm clean exit path for security review before adopting.

---

## Simulation Transcript

### Step 1: Casey evaluates exit path as part of adoption decision

Casey's evaluation: "Before we put 12 companies into this platform, I need to know we can get them out cleanly." This is a standard enterprise procurement requirement — exit strategy.

### Step 2: Casey navigates to the deletion flow

Casey goes to `/privacy` and finds the "Delete My Data" button. Casey examines the modal.

### Step 3: Casey identifies the per-product deletion model

The deletion modal says "permanently schedule deletion of all your product data." This is per-product. For 12 products, Casey would need to:
1. Switch to each product
2. Navigate to `/privacy` for each
3. Click "Delete My Data" for each
4. Confirm each deletion individually

**No "Delete Organization" or "Close Account" flow.** Journey 10 specifies "Delete Organization" as the entry point. This does not exist. Only per-product deletion exists from the UI.

### Step 4: Casey checks the GDPR deletion job

Casey (being technical, 7/10) might discover that `src/jobs/gdpr.ts` has `processAccountDeletions()` which does operate at the founder level — deleting all products and all founder data. But this requires a `deletion_requests` table entry with `status='confirmed'`. There is no UI to create this entry. It appears to be a backend-only capability, potentially triggered by support intervention.

### Step 5: Casey evaluates data retention after deletion

Casey's security review requires knowing:
1. What happens to data after deletion? The code shows: product data is deleted from ~14 tables, then `products.status='deleted'`. But the product row itself persists.
2. Is the founder record deleted? No — the privacy page deletion does not touch the `founders` table.
3. Are GitHub tokens revoked? `github_access_token` is set to NULL in the product row, but the token is not revoked via GitHub API. It remains valid on GitHub's side.
4. Are Stripe records cleaned up? No — the founder's `stripe_customer_id` persists, and the subscription is not cancelled.

**Casey's security review finding:** "Deletion is incomplete. The platform retains the founder record, Stripe customer ID, and does not revoke GitHub tokens. An attacker who compromises the database post-deletion could find orphaned credentials."

### Step 6: Casey checks for deletion confirmation and audit trail

No deletion receipt. No confirmation email. No audit trail entry accessible post-deletion (the `agent_audit_log` entry is on the deleted product and becomes inaccessible).

### Step 7: Casey's adoption recommendation

Casey's report to CTO: "Exit path is inadequate for enterprise deployment. Key concerns:
- No organization-level deletion (must delete each product individually)
- Billing continues after deletion
- GitHub credentials not revoked
- No deletion receipt or audit trail
- No recovery window management
Recommendation: Do not adopt until exit path is production-grade."

---

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | CRITICAL | **No organization-level deletion.** Only per-product deletion exists from UI. For 12 products, this is 12 separate deletion flows. |
| 2 | CRITICAL | **Founder record not deleted.** The privacy page deletion only targets product data. The founder's email, name, Stripe customer ID, and preferences persist. |
| 3 | CRITICAL | **GitHub tokens not revoked via API.** Token is NULLed in the database but not revoked on GitHub. The token remains valid for repo access until it naturally expires or is manually revoked. |
| 4 | CRITICAL | **Billing continues** (same as Run 080). The Stripe subscription is not cancelled as part of the deletion flow. |
| 5 | HIGH | **No deletion receipt.** Enterprise security review requires proof of deletion. No email, no downloadable receipt, no timestamp confirmation. |
| 6 | HIGH | **GDPR-level deletion exists in backend but is unreachable from UI.** The `processAccountDeletions` function in `gdpr.ts` is comprehensive but requires a `deletion_requests` entry that no UI creates. |
| 7 | HIGH | **Post-deletion credential exposure.** Orphaned `stripe_customer_id` and (until NULLed by async job) `github_access_token` remain in the database. |

## Cross-Company Awareness Check

For Casey's 12-product scenario, the per-product deletion model ensures each product is deleted independently. However:
- The `decision_patterns` table stores global patterns — deleting Product A does not remove its contributed patterns. Other founders' products may still be influenced by patterns from a deleted product.
- Portfolio memberships (`portfolio_memberships` table) are not cleaned up by either deletion path.

**CRITICAL boundary issue:** Patterns from deleted products remain in the global decision_patterns pool and continue to influence other founders' recommendations.

## Verdict: JOURNEY FAILED — Deletion is incomplete, credential cleanup missing, no org-level flow. Enterprise adoption blocked.
