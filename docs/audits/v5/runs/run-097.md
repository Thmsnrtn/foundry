# Run 097 — Robin (P10) x Company Retirement (J07)

**Persona:** Robin — frustrated user about to churn, Growth tier, 1 company (down from 2)
**Journey:** Company retirement / archival
**Severity Baseline:** Robin already removed one company and is considering retiring the last one.

---

## Simulation Transcript

### Step 1: Robin's experience removing the first company

Robin previously "removed" one company. How did Robin accomplish this? The codebase offers only one self-service path: "Delete My Data" on the privacy page. This schedules hard deletion, not retirement.

Robin likely used this path and experienced:
- No "retire and archive" option
- Permanent deletion scheduled (data loss after 30 days)
- No read-only archive access to historical data
- No billing adjustment (flat-rate tier)
- Agents may have continued running during the grace period

This experience — painful, lossy, no middle ground — likely contributed to Robin's frustration.

### Step 2: Robin considers retiring the last company

Robin has one company remaining. Robin is not ready to delete everything (that is Journey 10). Robin might want to:
- Pause the agents (stop the busywork decision queue)
- Keep the data for reference
- Stop paying for a while
- Maybe come back later

None of these options exist. The choices are:
1. Keep paying $199/mo and ignore the agents
2. Delete everything and lose all data
3. Cancel billing separately via Stripe but keep the account (agents keep running on the unpaid account until... what happens? The tier gate might restrict features but SCP agents have no billing-aware shutdown.)

### Step 3: Robin looks for a "pause my account" option

No pause exists. No "hibernate" or "hold" state. The SCP scheduler runs hourly on all active products regardless of billing status. There is no billing-aware agent shutdown.

**Codebase evidence:** `src/services/scp/scheduler.ts` — the scheduler queries for products and runs agents. It does not check billing status or subscription state before running agents.

### Step 4: Robin evaluates the "just cancel billing" approach

Robin could:
1. Go to Settings > Manage Subscription > Cancel via Stripe
2. Leave the Foundry account active

What happens? The `tier` field in the `founders` table would be updated (if the Stripe webhook handles cancellation correctly). With a null/empty tier, the tier gate middleware might block dashboard access. Or it might not — depending on how tier-gating handles cancelled subscriptions.

**Codebase evidence:** The Stripe webhook in `src/services/integrations/stripe-webhook.ts` handles `checkout.session.completed` but it is unclear if it handles `customer.subscription.deleted` to revoke the tier. This is a potential hole where agents continue running on a cancelled subscription.

---

## Findings

| # | Severity | Finding |
|---|----------|---------|
| 1 | CRITICAL | **No retirement/archival flow** (same as all J07 runs). |
| 2 | CRITICAL | **No account pause/hibernate.** Robin cannot temporarily stop agents and billing without permanently deleting data. |
| 3 | HIGH | **Billing cancellation may not stop agents.** The SCP scheduler does not check billing status. Cancelling the Stripe subscription may leave agents running indefinitely on a cancelled account. |
| 4 | HIGH | **Robin's first product removal was traumatic.** The only available path (hard deletion) contributes to churn frustration. If retirement had been available, Robin might have retired instead of deleted, and might still be a paying customer. |
| 5 | MEDIUM | **No re-entry path.** If Robin cancels and later wants to return, the onboarding flow starts from scratch. No "reactivate your paused account" experience. |

## Cross-Company Awareness Check

Robin went from 2 products to 1. The removed product's data was deleted (or scheduled for deletion). No cross-company boundary issue in the current state. However, the lack of retirement (vs. deletion) means Robin lost the option to preserve historical data from the first product for comparison with the second.

## Verdict: JOURNEY FAILED — No retirement, no pause, no hibernate. Binary choice: keep paying or lose everything.
