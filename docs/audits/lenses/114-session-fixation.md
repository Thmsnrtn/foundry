# Lens 114 — Session Fixation

**Auditor Persona:** Security Depth (Tier 3)
**Date:** 2026-04-16
**Scope:** Can an attacker set a victim's session cookie before they authenticate?

---

## Executive Summary

Session fixation risk is low because Foundry delegates authentication entirely to Clerk. The `__session` cookie is set by Clerk's client-side JavaScript after successful authentication, not by the Foundry server. An attacker cannot pre-set this cookie because: (1) Clerk generates session tokens server-side after authentication, (2) the token contains a signed JWT that the Foundry server validates via `verifyToken()`. However, the CSRF token (`foundry_csrf`) uses a double-submit cookie pattern where the server generates a new token if none is present in the cookie. An attacker could theoretically set a CSRF cookie via a subdomain or network interception, but this would only allow the attacker to know the CSRF token — not authenticate as the victim.

---

## Findings

### SFIX-01 — Clerk-managed sessions are not fixable (Severity: None)

**Description:** Clerk manages the `__session` cookie entirely on the client side after successful OAuth or password authentication. The JWT in the cookie is signed by Clerk's servers and validated by the Foundry backend using `verifyToken()`. An attacker cannot pre-set a valid `__session` cookie.

**Evidence:**
- `src/middleware/auth.ts:64-67`: `verifyToken(token, { secretKey, issuer: (iss: string) => iss.includes('clerk') })` — server validates JWT signature.
- `src/routes/auth/clerk.ts:38-46`: Clerk JS handles signup flow, sets `__session` only after Clerk server confirms authentication.

**Remediation:** None needed. Clerk's architecture prevents session fixation.

---

### SFIX-02 — CSRF cookie could be pre-set but impact is limited (Severity: Low)

**Description:** The CSRF middleware reads the token from the cookie and generates a new one if absent. If an attacker can set the `foundry_csrf` cookie (e.g., via a sibling subdomain or network interception), they would know the CSRF token value. However, the double-submit pattern requires the same token in both the cookie and the form field/header. Since the attacker cannot inject form fields into Foundry's server-rendered pages (Hono auto-escapes), they cannot submit cross-origin requests with matching cookie + header values.

**Evidence:**
- `src/middleware/csrf.ts:22`: Token read from cookie: `const match = cookieHeader.match(...)`.
- `src/middleware/csrf.ts:25-27`: New token generated if missing. No check that the token was generated by this server.

**Remediation:** Bind the CSRF token to the session: derive it from the Clerk session token using HMAC. This ensures the CSRF token is unpredictable even if an attacker can set the cookie.

---

### SFIX-03 — OAuth state parameter protects GitHub flow (Severity: None)

**Description:** The GitHub OAuth flow uses a random state parameter stored in the database with a 10-minute expiry. This prevents OAuth CSRF (where an attacker initiates an OAuth flow and tricks the victim into completing it, binding the attacker's GitHub account).

**Evidence:**
- `src/routes/dashboard/onboarding.ts:57-60`: `const oauthState = randomBytes(32).toString('hex')` with database storage and expiry.

**Remediation:** None needed. The GitHub OAuth flow is protected against session fixation and CSRF.

---

### SFIX-04 — Auto-provisioning on first login has no fixation vector (Severity: None)

**Description:** The auto-provisioning in auth middleware creates a founder record on first login if the webhook has not arrived. This uses the Clerk user ID from the validated JWT. An attacker cannot trigger auto-provisioning for a victim because they would need a valid JWT for the victim's Clerk account.

**Evidence:**
- `src/middleware/auth.ts:82-101`: Auto-provision uses `clerkUserId` from the validated JWT payload.

**Remediation:** None needed.

---

## Embarrassment Test

An attacker discovers that Foundry uses `foundry_csrf` cookie. They try to pre-set it via a `*.foundry.app` subdomain. The CSRF token they set is now in the cookie, but they cannot submit forms on the victim's behalf because Hono's server-rendered forms contain the server's version of the token (which matches the cookie they set). Wait — actually, if the attacker sets the cookie and knows the value, and the server trusts this value and embeds it in forms, then the attacker knows the CSRF token and could craft a cross-origin form submission... **This is theoretically exploitable if the attacker can both set the cookie and observe the token value.** In practice, the SameSite=Lax attribute on the cookie prevents most cross-origin scenarios.

## Pride Test

Delegating session management to Clerk eliminates the most common session fixation vectors. The OAuth state parameter implementation is textbook correct. The CSRF double-submit pattern is well-implemented.

## Distinct-Value Declaration

This lens confirms that Clerk-based authentication is structurally resistant to session fixation and identifies the one theoretical weakness: CSRF token not bound to session. The practical exploitability is very low due to SameSite cookie attribute.

## Tenancy-Critical Flag

**No.** Session fixation, if exploitable, would give an attacker access to a single founder's session. No cross-tenant escalation is possible because the session is bound to a single Clerk user ID.
