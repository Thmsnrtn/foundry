# Lens 134 — Tenant-Isolation Chaos Adversary

**Auditor perspective:** Edge-case hunter / domain adversary — creative cross-tenant bleed through timing, cache, logs, and metrics
**Distinct-value declaration:** Attempts to cause cross-tenant data leakage through unconventional vectors: timing attacks on shared in-memory state, cache key collisions, log aggregation, and metric contamination. Distinct from lens 44 (access control) and lens 127 (statistical leakage).
**Tenancy-critical:** Yes. This is the core multi-tenant isolation test.

**Date:** 2026-04-16
**Repo:** foundry (Hono + Turso + Clerk + Anthropic)

## TI-01. Shared in-memory AI spend tracker resets on deploy -- no cross-tenant bleed but cost ceiling bypass

**Severity: P2**
**Files:** `src/services/ai/client.ts:20-44`

The `dailySpend` Map is keyed by `productId`, so Company A cannot directly affect Company B's spend tracking. However, the Map resets on every deploy. If two companies are mid-day with high AI consumption and a deploy occurs, both lose their spend history and can exceed the daily ceiling.

This is not a cross-tenant bleed but a shared-infrastructure issue: the deploy event affects all tenants equally and unpredictably.

---

## TI-02. Shared Node.js event loop: one company's slow AI call blocks all others

**Severity: P1**
**Files:** `src/services/scp/scheduler.ts:39-51`

The hourly agent runner processes products sequentially in a single Node.js process. If Company A's agent run triggers a slow Anthropic API call (e.g., 120-second timeout), all other companies' agent runs are delayed. Additionally, HTTP requests from Company B's founder are served from the same event loop and may experience increased latency during Company A's heavy AI processing.

While the AI calls are async (non-blocking), the sequential product loop means Company A's completion gates Company B's start. There is no priority system, no timeout per product, and no isolation between product processing.

**Evidence:**
- `src/services/scp/scheduler.ts:39-51`: `for (const row of result.rows)` -- sequential
- `src/services/ai/client.ts:48`: `AI_TIMEOUT_MS = 120000` (2 minutes default)
- Single Hono HTTP server shares the event loop with all job execution

## TI-03. `decision_patterns` table allows any product to influence any other product's decisions

**Severity: P2**
**Files:** `src/db/client.ts:210-250`, `src/services/decisions/patterns.ts`

The `decision_patterns` table is a global cross-tenant table by design. However, a malicious founder could game the system:

1. Create many products (if tier enforcement is bypassed)
2. Make specific decisions with manufactured outcomes
3. Flood the `decision_patterns` table with biased data
4. Other founders' decision recommendations would be influenced by the biased patterns

There is no rate limit on pattern contribution, no quality filter, and no per-founder contribution cap.

**Evidence:**
- `src/services/decisions/patterns.ts`: `generatePatternFromOutcome` writes to global table
- No `founder_id` or `product_id` filter on pattern queries
- Patterns weighted by `confidence DESC` -- a founder who logs many outcomes builds high confidence scores

## TI-04. Log output mixes all tenants' data in shared stdout

**Severity: P2**
**Files:** `src/jobs/index.ts` (throughout)

All structured log entries go to stdout. Product names, IDs, risk states, signal scores, and error messages are interleaved across all companies. Anyone with log access (Fly.io dashboard, log drain) sees all companies' operational data.

This is documented in lens 44 (MTI-06) but the chaos adversary angle is: could a malicious Fly.io team member or compromised log drain extract business intelligence about specific Foundry customers?

**Specific data exposed in logs:**
- Product names: `lifecycle_check: AcmeApp activated: revenue_metrics` (line 49)
- Risk transitions: `weekly_synthesis: AcmeApp -- risk green->red` (line 149)
- Signal scores: logged in `signalAlertCheck` (line 653)
- AI insight headlines: `daily_insight_generate: generated for AcmeApp -- "Revenue concentration risk..."` (line 789)

## TI-05. Cache key collision: productId-based caches could collide if IDs collide

**Severity: P3**
**Files:** `src/services/signal.ts:45`

The prose cache uses `productId` as the key. Product IDs are generated by `nanoid()` (21 characters, ~126 bits of entropy). The collision probability at 25 products is negligible (~10^-34). At 1 million products: still negligible.

This is not a practical attack vector but is noted for completeness.

---

## TI-06. `SELECT *` returns columns that may contain other tenants' references

**Severity: P3**

Some tables (e.g., `decision_patterns`, `benchmark_pool`) intentionally contain cross-tenant data. When a service fetches from these tables, the response may include data derived from other tenants. This is by design for the intelligence layer but creates a theoretical information channel.

The `market_category` field in `decision_patterns` is particularly risky: if a founder knows they are the only Foundry customer in "dental SaaS", any pattern with `market_category='dental SaaS'` reveals their competitors' decision outcomes.

---

## Recommendations

1. **Add per-product timeout to the agent runner** -- If a product's agent run exceeds 5 minutes, skip remaining agents and move to the next product. Prevents one company from blocking the fleet.
2. **Separate job execution from the HTTP process** -- Run scheduled jobs in a dedicated Fly.io machine or background worker. The HTTP server should only serve requests.
3. **Add per-founder contribution caps to decision_patterns** -- Max 50 pattern contributions per product per month. Weight patterns by diversity of contributing products, not just confidence.
4. **Implement tenant-scoped log prefixes** -- Use a structured log format where `productId` is a JSON field, enabling log filtering by tenant. Consider log partitioning for sensitive data.
5. **Remove `market_category` from decision_patterns queries** -- Or require minimum 5 products per category before including it in pattern matching.
