# Lens 089 — Transactional Email Deliverability

**Distinct value:** Audits the full email delivery pipeline: Resend configuration, from-address domain verification, SPF/DKIM implications, template quality (HTML rendering, text fallback, mobile), and the gap between "email sent" and "email delivered and read." No other lens examines the email infrastructure end-to-end.

**Tenancy-critical:** No. Email is per-founder, not per-product. The from address is global (`noreply@foundry.app` or `briefings@foundry.app`), not tenant-specific.

## Executive Summary

Foundry uses Resend for transactional email with a fallback to SendGrid for weekly digests. The email infrastructure has structural issues: (1) two different from addresses are used (`noreply@foundry.app` for agent emails, `briefings@foundry.app` for digests) which requires both to be verified with SPF/DKIM, (2) there is no bounce handling or suppression list management, (3) the weekly digest HTML template is well-crafted but the agent action emails have no HTML template at all (raw `parameters.html` from the agent is sent directly), (4) there is no unsubscribe mechanism despite sending weekly digests (CAN-SPAM violation), and (5) the `RESEND_FROM_ADDRESS` env var exists but is never used — the from address is hardcoded in two places.

## Findings

### TED-01 Two Hardcoded From Addresses, Neither Uses RESEND_FROM_ADDRESS
- **Severity:** P1
- **Description:** The environment validation references `RESEND_FROM_ADDRESS` as an optional env var, but neither email sending path uses it. The Resend integration (`src/services/integration/resend.ts:164`) hardcodes `Foundry <noreply@foundry.app>`. The weekly digest sender (`src/services/scp/briefing/email-digest.ts:319`) hardcodes `Foundry <briefings@foundry.app>`. Both addresses must have DNS records (SPF/DKIM) configured for `foundry.app`, but there is no code that verifies this or falls back to the env var address.
- **Evidence:** `src/services/integration/resend.ts:164` — `from: (parameters.from as string) ?? 'Foundry <noreply@foundry.app>'`. `src/services/scp/briefing/email-digest.ts:319` — `from: 'Foundry <briefings@foundry.app>'`. `src/env.ts:28` — `RESEND_FROM_ADDRESS` listed but unused.
- **Remediation:** Use `process.env.RESEND_FROM_ADDRESS` as the single from address. Remove the second from address. Having one verified sending address simplifies DNS configuration and improves deliverability. The current two-address pattern requires two sets of DKIM records or a wildcard.

### TED-02 No Unsubscribe Mechanism (CAN-SPAM / GDPR Risk)
- **Severity:** P0
- **Description:** The weekly email digest is sent to founders automatically with no way to opt out. There is no unsubscribe link in the email footer, no preference center, and no database column tracking email preferences. The email footer says "Reply to this email to respond to your advisor" but does not include an unsubscribe option. Under CAN-SPAM (US), every commercial email must include a clear unsubscribe mechanism. Under GDPR (EU), consent must be freely given and withdrawable.
- **Evidence:** `src/services/scp/briefing/email-digest.ts:84-88` — footer HTML has no unsubscribe link. No `email_preferences` column on founders table. No route for managing email preferences.
- **Remediation:** Add an unsubscribe link to every email footer. Implement a one-click unsubscribe via a signed URL (e.g., `/email/unsubscribe?token=...`). Add `email_digest_opted_out` boolean to founders table. Check this flag before sending digests. Also add the `List-Unsubscribe` header to all emails for email client native unsubscribe.

### TED-03 Agent Action Emails Have No Template
- **Severity:** P2
- **Description:** When an agent email action is executed (`src/services/integration/resend.ts:155-170`), the email is sent with whatever `parameters.html` the agent provided. This HTML is generated by the LLM as part of the agent's output. There is no wrapping template, no consistent branding, no footer, and no guarantee the HTML is well-formed or mobile-responsive. The raw LLM-generated HTML could contain any structure.
- **Evidence:** `src/services/integration/resend.ts:160-168` — the Resend API call sends `html: parameters.html` directly. The HTML comes from `outbound_actions.parameters_json` which is set by the agent.
- **Remediation:** Wrap all outbound emails in the same template used for digests (`wrapHtml()` from `email-digest.ts`). This ensures consistent branding, footer with unsubscribe, and mobile-responsive layout regardless of what the agent generates.

### TED-04 No Bounce or Complaint Handling
- **Severity:** P2
- **Description:** Resend provides webhooks for delivery events (bounced, complained, etc.). The Resend integration tracks email metrics (`getEmailMetrics()` counts sent/delivered/opened/clicked from `integration_events`) but there is no handler for bounces or complaints. Hard bounces should trigger email suppression (stop sending to that address). Spam complaints should trigger immediate suppression and review. Without this, Foundry will continue sending to invalid addresses, hurting sender reputation.
- **Evidence:** `src/services/integration/resend.ts:216-259` — `getEmailMetrics()` reads `integration_events` but only counts delivered/opened/clicked. No bounce or complaint event handling. No suppression list.
- **Remediation:** Handle Resend webhook events for `email.bounced` and `email.complained`. On hard bounce, mark the founder's email as suppressed and stop all sends. On complaint, supppress and alert. Maintain a suppression list checked before every send.

### TED-05 SendGrid Fallback Has No Error Differentiation
- **Severity:** P3
- **Description:** The `sendViaSendGrid()` function (`src/services/scp/briefing/email-digest.ts:333-361`) catches non-200 responses but treats all errors identically. A 401 (bad API key) is handled the same as a 429 (rate limited) or 400 (invalid recipient). The error message includes the status code but the caller has no retry logic for transient errors.
- **Evidence:** `src/services/scp/briefing/email-digest.ts:354-359` — throws on any non-ok response with no status differentiation.
- **Remediation:** Differentiate transient (429, 500, 502, 503) from permanent (400, 401, 403) errors. Use the `withRetry` utility for transient errors. Log permanent errors as configuration issues.

### TED-06 Email Digest Storage Failure Is Silently Swallowed
- **Severity:** P3
- **Description:** After sending an email digest, the code attempts to store it in the `email_digests` table. The INSERT is wrapped in a try/catch that silently swallows the error. If the table does not exist (the `ensureTable()` call uses a runtime CREATE TABLE), the digest history will be empty despite emails being sent. The comment says "non-fatal — email was sent, storage failure is secondary" which is technically correct but means the digest history feature is unreliable.
- **Evidence:** `src/services/scp/briefing/email-digest.ts:390-398` — empty catch block after INSERT.
- **Remediation:** Log the storage failure at warning level. The `ensureTable()` pattern (CREATE TABLE IF NOT EXISTS at runtime) is fragile — this should be a proper migration.

## Email Template Quality Assessment

| Aspect | Weekly Digest | Agent Action Emails |
|---|---|---|
| HTML template | Well-structured, branded header/footer, proper table layout | No template, raw LLM HTML |
| Text fallback | Generated by AI alongside HTML | None |
| Mobile responsive | Table-based layout, 600px max-width, works on mobile | Unknown, depends on LLM output |
| Preheader text | Yes, AI-generated | No |
| Unsubscribe link | No | No |
| Reply-to handling | Footer says "reply to respond" | Not configured |
| From address | `briefings@foundry.app` | `noreply@foundry.app` |

## Positive Findings

- The weekly digest template (`wrapHtml()`) is genuinely well-crafted HTML email. The inline styles, table-based layout, and semantic structure follow email best practices.
- AI-generated digest content is contextual and personalized per product, not generic.
- The Resend integration uses `withRetry` for the actual API call, which is correct.
- Email metrics tracking (sent, delivered, opened, clicked) from Resend webhooks is a good foundation.
